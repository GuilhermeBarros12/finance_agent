# T08 — Migrations do banco

## O que foi feito
Três migrations em `supabase/migrations/` criam o banco da fatia: dados de mercado compartilhados, dados privados por usuário, e RLS com grants. Um `supabase/seed.sql` carrega dois ativos fictícios (`DEMO3`, `TEST4`) e um snapshot publicado com um campo `verified`, um `divergent`, um `incomparable` e um `missing`. Os testes pgTAP ficam em `supabase/tests/database/001_rls_e_integridade.test.sql`.

O dicionário de dados (`docs/data-dictionary.md`) e a visão geral (`docs/architecture/visao-geral.md`) nasceram nesta tarefa.

## Por que foi feito assim
- Chaves `uuid`; fontes e ativos têm também um código legível (`code`, `symbol`) porque o contrato Python usa ids em texto; o mapeamento fica para a RPC da T09.
- Imutabilidade por trigger em `snapshots`, `observations` e `field_validations` (README 6.4). A exceção da retenção é a variável de transação `app.retention_job`, que libera só o DELETE; update e insert continuam rejeitados com ela ligada. O FK de `selected_observation_id` perdeu o `on delete set null` e há trigger contra `truncate`. Funções de trigger têm `execute` revogado de public, anon e authenticated. Estendi o trigger às observações e validações porque proteger só a linha do snapshot deixaria o conteúdo mutável.
- Checks no banco espelham o contrato da T06: unidade por métrica, `divergent` sem observação escolhida, comparação obrigatória só em `verified`/`divergent`, hash SHA-256. Um campo não herda a validação de outro: a unicidade é por `(snapshot, ativo, métrica)`.
- RLS padrão do README 8.3 com `allowed_users` no lugar de `beta_users`. Grants por coluna (`insert (user_id, title)`, `update (title)`). `messages`, `request_runs` e `llm_usage` sem escrita do cliente (D21, E14 a E16).
- A FK de `portfolio_items.asset_id` para `assets` é verificada pelo dono da tabela, então funciona mesmo sem o usuário poder ler `assets`.

## O que foi descartado
- `relatorios_pdf`, Storage e `usage_counters` por usuário (proibidos pela tarefa).
- Validar no banco que `active_snapshot` aponta só para snapshot publicado: fica para a RPC da T09, que publica de forma atômica.

## Arquivos principais
- `supabase/migrations/20261114000001_market_data.sql`: tabelas de mercado e triggers de imutabilidade.
- `supabase/migrations/20261114000002_private_data.sql`: tabelas privadas, FK composta, `touch_updated_at`.
- `supabase/migrations/20261114000003_rls_grants.sql`: RLS, grants, `is_allowed_user()`, políticas.
- `supabase/seed.sql`: dados sintéticos.
- `supabase/tests/database/001_rls_e_integridade.test.sql`: 31 testes pgTAP.
- `docs/data-dictionary.md`, `docs/architecture/visao-geral.md`.

## Como conferir
```bash
npx supabase start
npx supabase db reset     # aplica as três migrations e o seed sem erro
npx supabase test db      # 31 testes pgTAP, resultado PASS
```

## Limitações e pontos de atenção
- O papel do coletor e a RPC de publicação são da T09; hoje `service_role` mantém todos os privilégios nas tabelas de mercado (só anon e authenticated foram revogados), além do superusuário. A RPC da T09 deve validar que `selected_observation_id`/`observation_ids` pertencem ao mesmo snapshot e métrica.
- `supabase/migrations/.gitkeep` foi mantido; o CLI o ignora.
- Ao adicionar uma tabela em `public`, revogue os grants padrão de `anon` e `authenticated`; o Supabase os concede automaticamente.

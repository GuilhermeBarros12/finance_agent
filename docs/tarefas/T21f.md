# T21f — Testes ponta a ponta e capturas de tela

## O que foi feito
Playwright na raiz (`playwright.config.ts`, testes em `tests/e2e/`) percorre o sistema inteiro em ambiente local: Supabase local com o `seed.sql`, os handlers reais de `agent` e `catalog` com `MOCK_LLM=true`, e o front em modo de desenvolvimento. Há dez testes em `roteiros.spec.ts`: os seis roteiros do plano (a a f), o da tela de login, e três de invariantes e falhas. `capturas.spec.ts` gera as imagens de cada tela, e 44 PNG ficaram em `docs/capturas/` (prefixo `t21f-`, 1,3 MB no total).

Roteiros: (a) criar conversa, enviar seleção, ver os quatro estados do seed (Conferido, Divergente, Não comparável, Sem dado) e recarregar; (b) pergunta em texto, com a resposta do classificador simulado (DEMO3 + dividend_yield, `intent_source: "mock"`); (c) `needs_selection` com o motivo "O modo por IA está desligado." e uso do seletor; (d) carteira com DEMO3 e TEST4 e "Atualizar carteira"; (e) painel `/dados`; (f) exportação, com o JSON baixado conferido. Extras: a carteira e `user_id` nunca aparecem em corpo enviado ao `/agent`; falha de rede deixa a tela usável e o reenvio reusa o `request_id`; falha do catálogo mostra erro e se recupera; a tela de login não tem campo de senha.

O job `e2e` entrou no `ci.yml` (ver a seção "CI: o que falhou na primeira execução real"), roda só se `playwright.config.ts` existe (saída `e2e` do job `detect`) e está em `needs` de `ci-ok`.

## Por que foi feito assim
- **Gateway local em Deno** (`tests/e2e/support/functions-gateway.ts`). `supabase functions serve` não funciona no ambiente onde a tarefa foi feita: o contêiner do edge runtime não baixa o supabase-js pelo proxy de rede (UnknownIssuer). Em máquina sem esse limite, `functions serve` poderia ser usado (a CI poderia adotá-lo); o gateway foi escolhido para que os testes rodem igual nos dois lugares. Ele importa `handler.ts` e `store.ts` de cada função (os mesmos módulos do `index.ts`) e apenas roteia `/functions/v1/<nome>`, com o CORS do próprio handler. Os handlers e o banco são reais, nada é simulado além do LLM (`MOCK_LLM=true`, `APP_ENV=local`, validado por `resolveLlmConfig`).
- **O gateway também repassa REST e Auth** ao Supabase local. O front usa um único endereço (`VITE_SUPABASE_URL` aponta para o gateway), sem `page.route`, sem mexer na CORS dos handlers. As requisições do navegador podem ser capturadas como são.
- **needs_selection de verdade.** O gateway tem um controle só de teste (`POST /__e2e/llm-mode`, em 127.0.0.1) que troca o agente entre o simulado e "LLM desligado" (configuração sem chave), caminho real que produz `LLM_DISABLED`. A fixture volta ao simulado ao fim de cada teste.
- **Login.** Cada teste cria um usuário novo pela API administrativa do Supabase local (chave lida de `supabase status -o json` em tempo de execução, nunca gravada), com senha aleatória, insere em `allowed_users`, faz o `grant_type=password` no Node (a mesma chamada do `signInWithPassword`) e grava a sessão no `localStorage` com a chave do supabase-js (`sb-127-auth-token`). O usuário é apagado no fim (cascata limpa conversas, mensagens, carteira e execuções), então nenhum teste vaza para outro e o seed não é alterado. `supabase/config.toml` já tinha `[auth.email]` habilitado (configuração local); nada foi mudado e a tela de login continua só com Google (há um teste para isso).
- **Dev server, não preview.** Segue o plano; evita rebuild por teste. As variáveis `VITE_*` (só endereço do gateway e chave anônima local) vêm do ambiente do processo.
- **Sem esperas fixas.** Só `expect` com repetição, papéis, textos e `waitForResponse`. A data de hoje não entra: o seed tem `collected_at` fixo (18/09/2026), a idade é conferida só pelo formato ("há N dias") e o estado de atualização, calculado pelo servidor, aceita qualquer um dos quatro (hoje aparece "Vencido").
- **Capturas.** 1280x720 e 390x844, escala 1x, só a viewport, exceto `tabela-estados`, de página inteira, porque precisa mostrar na mesma imagem os quatro estados. Por padrão gravam em `test-results/capturas` (ignorado pelo git); `npm run e2e:capturas` grava em `docs/capturas`. Os PNG foram reduzidos a 96 cores com `scripts/e2e/otimizar_capturas.py` (3,7 MB para 1,3 MB).

## O que foi descartado
- `supabase functions serve` (limite do ambiente, acima).
- `page.route` para encaminhar chamadas de função: depende do tratamento de CORS do Playwright e esconde a rota real.
- Habilitar e-mail e senha na tela ou em ambiente hospedado: proibido pela tarefa.
- Upload dos artefatos de falha na CI: não há Action de upload fixada no `ci.yml` e não foi possível confirmar o SHA completo de uma, então o job só imprime o resultado.

## Como conferir
```bash
npm ci && npm ci --prefix frontend
npx playwright install chromium          # fora do ambiente de desenvolvimento deste repositório
npx supabase start && npx supabase db reset
npm run e2e                               # roteiros + capturas (em test-results/capturas)
npm run e2e:capturas                      # grava em docs/capturas
python3 -I scripts/e2e/otimizar_capturas.py docs/capturas/t21f-*.png
```
Variáveis opcionais: `DENO_BIN` (caminho do `deno`, padrão `deno`) e `PW_CHROMIUM_PATH` (Chromium fora do caminho padrão do Playwright). As portas 54331 (gateway) e 5173 (front) precisam estar livres.

## Limitações e pontos de atenção
- O job `e2e` da CI não foi executado: só passará (ou não) no pull request.
- A CI não envia relatórios nem capturas; falhas aparecem na saída do job.
- O LLM real, a brapi e as fontes reais nunca são chamados. O modo "desligado" cobre o `needs_selection`; erros do provedor não são exercitados aqui (estão nos testes Deno da T19).
- A página de chat sai muito alta na tabela completa; `tabela-estados` é a única captura de página inteira.
- Os testes usam um worker, porque compartilham o modo de LLM do gateway.

## CI: o que falhou na primeira execução real
Na primeira execução no pull request, o passo `supabase start` (CLI `latest` do `setup-cli`) baixou as imagens, subiu o banco e aplicou as migrations e o seed, mas falhou ao iniciar os containers: `failed to bind host port 0.0.0.0:54324/tcp: address already in use` (a caixa de e-mail local, inbucket/mailpit). A porta já estava ocupada no runner e o `start` completo derruba tudo. O job `database` não via isso porque usa só `supabase db start`.

Correção: o e2e não usa e-mail, Studio, Realtime, Storage, edge runtime, analytics, vector nem pooler. O job agora roda `npx supabase start -x realtime,storage-api,imgproxy,mailpit,postgres-meta,studio,edge-runtime,logflare,vector,supavisor`, que deixa só o banco (54322), o Auth (gotrue), o REST (postgrest) e o Kong (54321). Os nomes vêm de `npx supabase start --help` da CLI 3.1.0 da raiz. O job passou a usar essa mesma CLI (npx, versão travada no lock) para subir os containers, ler `supabase status` e parar, e o uso de `supabase/setup-cli` saiu do job (nenhum passo restante o exige). Há um passo de diagnóstico (`docker ps` e a `API_URL`, com `if: always()`) e a parada também é `if: always()`.

Conferido localmente: `npx supabase stop --no-backup`, o `start -x` acima (subiram só `db`, `auth`, `rest` e `kong`), `npx supabase status` e `npm run e2e` (14 passed). Se a porta ocupada no runner fosse 54321 ou 54322, o job continuaria falhando; o diagnóstico mostraria isso, e a mitigação seria outra porta em `supabase/config.toml` para o job. Limitação honesta: só o próximo ciclo do pull request prova que o job passa na CI.

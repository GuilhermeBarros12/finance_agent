Aula de engenharia de software

Como o Agente de Investimentos é construído, e por quê

Este guia percorre o repositório como faríamos numa aula: primeiro o problema, depois os conceitos de arquitetura que vamos usar, e só então cada peça da stack e cada decisão. O objetivo não é decorar ferramentas. É entender por que cada escolha foi feita, para que você consiga defender, ou questionar, cada uma delas.

1O problema antes da solução

Toda boa arquitetura começa por uma pergunta: qual problema estamos resolvendo? Sem isso, escolhemos ferramentas por gosto e não por necessidade.

Quem pesquisa ações costuma abrir vários sites (Fundamentus, StatusInvest e outros) para ver indicadores como P/L (preço sobre lucro), P/VP (preço sobre valor patrimonial), dividend yield e ROE. O problema é sutil: dois sites podem mostrar o “mesmo” indicador com valores diferentes, porque usam fórmulas, janelas de tempo ou datas-base diferentes. Um dividend yield dos últimos doze meses não é o mesmo que o último dividendo anualizado, embora ambos se chamem “DY”.

Este projeto é uma aplicação web pessoal que:

  1. coleta esses indicadores em mais de uma fonte, uma vez por dia;
  2. compara as fontes campo a campo;
  3. mostra o resultado num chat, sempre com a fonte e a data de cada número;
  4. deixa explícito quando as fontes discordam, em vez de esconder a dúvida.
A frase que guia todo o resto

O README diz que o objetivo é reduzir o trabalho de juntar informações “sem esconder a incerteza dos dados”. Guarde essa frase. Quase toda decisão que veremos (usar decimal em vez de float, não deixar o LLM escrever números, não “consertar” divergências com média) existe para protegê-la.

Também é importante saber o que o sistema não é: não é corretora, não é terminal de cotação em tempo real, não recomenda investimentos e não guarda quanto você tem de cada ação. Delimitar o que fica de fora é parte do trabalho do arquiteto, e evita que o projeto cresça sem controle.

2Conceitos de base

Antes de olhar o código, vamos alinhar o vocabulário. Cada conceito abaixo aparece várias vezes no projeto.

Conceito: arquitetura de software

Arquitetura é o conjunto de decisões difíceis de mudar depois: como o sistema se divide em partes, como essas partes conversam, onde os dados moram e quem pode fazer o quê. Trocar a cor de um botão não é arquitetura. Escolher que o navegador nunca fala direto com a tabela de cotações é.

2.1 Separação de responsabilidades

Cada parte do sistema deve ter um motivo para existir e um conjunto claro de coisas que não faz. Aqui, o coletor busca dados e nunca responde a usuários; o backend responde a usuários e nunca faz scraping; o navegador mostra coisas e nunca recebe chaves secretas. Quando uma parte quebra, sabemos onde procurar, e uma mudança numa ponta não derruba a outra.

2.2 Processamento em lote versus processamento sob demanda

Existem dois ritmos de trabalho no sistema:

  • Lote (batch): uma vez por dia, à noite, um programa roda, coleta tudo, valida e grava. Ninguém está esperando na tela.
  • Sob demanda (request/response): o usuário faz uma pergunta e espera a resposta em segundos.

Separar os dois é uma das decisões mais importantes do projeto. A pergunta do usuário nunca dispara uma coleta: ela só lê o que o lote já preparou. Isso deixa a resposta rápida e previsível e evita martelar os sites de origem a cada clique.

Analogia

Pense numa padaria. O pão é assado de madrugada (lote). Quando o cliente chega, o atendente só pega o pão pronto da prateleira (sob demanda). Ninguém liga o forno porque um cliente entrou. A prateleira, aqui, se chama snapshot.

2.3 Contrato e fonte única da verdade

Um contrato é um acordo formal sobre o formato de um dado: quais campos existem, de que tipo, quais valores são permitidos. Quando duas linguagens (Python e TypeScript) precisam concordar sobre o mesmo dado, o perigo é cada uma ter sua própria definição e as duas irem se afastando sem ninguém perceber. A solução é ter uma fonte única da verdade, no caso os arquivos JSON Schema da pasta schemas/, e gerar ou testar o resto a partir dela.

2.4 Transação e atomicidade

Uma transação de banco é um grupo de operações que acontece por inteiro ou não acontece. Se o lote do dia tem 12 ações e falha no meio da gravação, o banco não pode ficar com 6 ações de hoje e 6 de ontem misturadas. Ou o snapshot novo entra inteiro, ou o anterior continua valendo. Isso se chama atomicidade.

2.5 Idempotência

Uma operação é idempotente quando repeti-la produz o mesmo efeito que fazê-la uma vez. Na internet, pedidos se repetem o tempo todo: a rede oscila, o usuário clica duas vezes, o navegador reenvia. Sem idempotência, a mesma pergunta viraria duas mensagens no histórico. O projeto resolve isso com um request_id que o navegador gera e o servidor registra.

2.6 Defesa em profundidade

Em segurança, nunca confiamos numa única barreira. Se o código do backend tiver um bug de permissão, o banco ainda deve recusar o acesso indevido. Se o banco for mal configurado, o backend ainda deve conferir quem é o usuário. São camadas que se protegem mutuamente.

2.7 Determinismo

Um sistema é determinístico quando a mesma entrada sempre produz a mesma saída. Modelos de linguagem (LLMs) não são determinísticos e podem “inventar” números com toda a confiança. Por isso, neste projeto, tudo o que mostra número é código determinístico. O LLM, quando entrar, só ajuda a entender a pergunta.

2.8 ADR: o diário de decisões

Um ADR (Architecture Decision Record) é um documento curto que registra uma decisão, o motivo e a consequência. O projeto tem dois: docs/adr/0001-primeira-fatia-acoes.md (decisões D1 a D21) e docs/adr/0002-execucao-autonoma.md (E1 a E20). Eles existem porque, seis meses depois, ninguém lembra por que algo foi feito, e uma decisão sem motivo registrado acaba sendo desfeita por engano.

3Visão geral: quatro blocos

O sistema tem quatro blocos. Olhe o diagrama com calma: é o mapa de tudo o que vem depois.

Coleta (collector/)

Busca nas fontes, transforma texto em número, compara as fontes e publica um snapshot. Não recebe perguntas, não chama LLM.

Persistência (supabase/migrations/)

Guarda dados de mercado (compartilhados e imutáveis) e dados privados de cada usuário (conversas, carteira). O snapshot publicado é o “cache oficial” da aplicação.

Backend (supabase/functions/)

Autentica, confere permissão, monta a resposta a partir do snapshot e grava a conversa. É o único caminho entre o usuário e os dados de mercado.

Frontend (frontend/)

Mostra conversas, tabelas, fontes e alertas. Não faz scraping, não recebe chaves privadas e não calcula valores financeiros.

Por que não há um servidor ligado o tempo todo?

Repare que não existe nenhum “servidor Python” rodando 24 horas. O coletor nasce, trabalha alguns minutos num runner do GitHub Actions e morre. As Edge Functions só existem enquanto atendem um pedido. Isso cabe nas camadas gratuitas dos serviços (o projeto tem uma política de custo zero) e elimina uma classe inteira de problemas: não há máquina para atualizar, reiniciar ou monitorar.

Atenção: por que float é proibido

Computadores guardam float em base 2, e muitas frações decimais simples não têm representação exata. Experimente no Python:

>>> 0.1 + 0.2
0.30000000000000004
>>> from decimal import Decimal
>>> Decimal("0.1") + Decimal("0.2")
Decimal('0.3')

Num sistema que decide se dois números “concordam” dentro de uma tolerância de 0,02, um erro na 17ª casa pode mudar o veredito. Por isso a regra é a mesma nas três camadas: Decimal no Python, numeric no banco e string no JSON. O número viaja como texto ("8.50") justamente para que nenhuma linguagem no caminho o converta em float sem querer. E é por isso que o navegador não faz contas com valores financeiros.

4.4 Automação: GitHub Actions

O GitHub Actions roda duas coisas: a CI (.github/workflows/ci.yml), que testa todo pull request, e no futuro o lote diário do coletor. Usar o runner do GitHub como “máquina que acorda à noite” evita ter um servidor só para isso. Todas as actions são fixadas por SHA completo, e não por tag, porque uma tag pode ser movida para um código malicioso e um SHA não pode.

4.5 A cola entre linguagens: JSON Schema

Os três arquivos em schemas/ (observation, validation e manifest) são a fonte única da verdade dos contratos. O fluxo é:

  1. Os modelos Pydantic em contracts.py são exportados como JSON Schema (scripts/export_schemas.py).
  2. Um script Node (scripts/generate_ts_types.mjs) gera os tipos TypeScript em supabase/functions/_shared/contracts.gen.ts.
  3. A CI confere se os schemas versionados estão atualizados e roda exemplos válidos e inválidos (schemas/examples/) contra os dois lados.

Se alguém mudar o contrato só no Python, a CI quebra. É assim que se evita a “divergência silenciosa” da decisão D8.

5A viagem de um dado: do site ao banco

Vamos seguir um único número, o P/L de uma ação, desde a página da fonte até o banco.

5.1 Adaptadores: separar buscar de interpretar

Cada fonte tem um adaptador que implementa a interface SourceAdapter (sources/base.py) com dois métodos separados:

class SourceAdapter(ABC):
    def fetch(self, assets) -> list[RawRecord]:
        """Busca as respostas brutas. Falha de rede lança exceção; nunca devolve vazio."""

    def parse(self, raw: RawRecord) -> list[Observation]:
        """Interpreta uma resposta bruta. Formato inesperado lança erro de parser."""
Conceito: o padrão Adapter

Cada site tem um formato diferente. O adapter converte esse formato particular numa linguagem comum (Observation), e o resto do sistema nunca precisa saber de onde o dado veio. Para adicionar uma fonte nova, escreve-se um adaptador novo e mais nada muda.

A separação entre fetch e parse é o que permite testar o parser com fixtures: arquivos com respostas de exemplo, escritos à mão, com tickers inventados como DEMO3 e TEST4 (collector/tests/fixtures/). A CI não acessa nenhum site real. Isso deixa os testes rápidos, reprodutíveis e independentes de o site estar no ar.

Repare também na docstring de fetch: “nunca devolve vazio”. Se a rede falha, o erro sobe. Um return [] silencioso faria a falha parecer “essa ação não tem dados”, e essa é justamente uma das regras do projeto: falha de coleta nunca vira zero, tabela vazia ou data de hoje.

5.2 A observação: um campo, uma fonte

A unidade básica de dado é a observação: um indicador, de um ativo, em uma fonte. Ela carrega não só o valor, mas a sua história (proveniência):

  • raw_value (o texto original) e value_decimal (o número normalizado);
  • reference_at (a data-base informada pela fonte) e collected_at (quando coletamos);
  • source_url, methodology_id, parser_version, run_id;
  • raw_content_hash, um hash do conteúdo usado.

Por que tanto metadado? Porque o produto inteiro é “mostrar de onde veio cada número”. Sem proveniência, isso seria impossível.

5.3 Normalização

“1.234,56” numa página brasileira significa mil duzentos e trinta e quatro. Numa página americana, “1.234” significaria um vírgula dois. O normalizador (normalization/numbers.py) precisa conhecer o formato de cada fonte em vez de fazer substituições cegas. Percentuais seguem uma convenção única: "8.50" com unidade percent, nunca 0.085 misturado com 8.5.

5.4 Validação por campo: o coração do sistema

O motor em validation/engine.py decide, para cada par (ativo, indicador), um estado. A regra mais importante está escrita no topo do arquivo: “nada aqui olha outra métrica ou outro ativo, então um campo nunca herda a validação de outro.”

A decisão segue uma escada. Primeiro verificamos se a comparação faz sentido; só depois comparamos números:

Mesmo ativo?
  → Mesmo conceito e unidade?
     → Mesma janela/metodologia?
        → Datas comparáveis?
           → Só agora: aplicar a tolerância numérica

E a tolerância é calculada assim (validation/tolerance.py):

delta_abs = abs(a - b)
limite    = max(atol, rtol * max(abs(a), abs(b)))

delta_abs <= limite  →  verified
delta_abs >  limite  →  divergent

atol é uma tolerância absoluta (por exemplo, 0,02 no P/VP) e rtol uma relativa (2% do valor). Usar o maior dos dois funciona bem tanto para números pequenos quanto para grandes. Os valores ficam em config/tolerances.yaml, versionados.

Os estados possíveis, cada um com nome próprio, sem depender só de cor:

EstadoQuandoO que a tela mostra
✓ verifiedDuas fontes comparáveis concordam dentro da tolerância.Um valor em destaque e as referências.
≠ divergentFontes comparáveis discordam além do limite.Os dois valores lado a lado, diferença e limite. Nenhum em destaque.
1 single_sourceSó uma fonte utilizável.O valor, com aviso de “não verificado”.
? incomparableHá dados, mas a comparação não é defensável.O motivo (janela, conceito, data).
— missingNenhuma observação utilizável.“Não disponível”. Nunca zero.
∅ not_applicableO indicador não se aplica ao ativo.O motivo explícito.
! invalidFalha de contrato ou de parsing.Fica fora da tabela principal; o erro é registrado.
Por que não tirar a média quando as fontes divergem?

Porque a média de dois números possivelmente errados é um terceiro número que nenhuma fonte publicou, apresentado como se fosse certo. Escolher a “fonte preferida” esconde a dúvida do mesmo jeito. Pedir ao LLM que decida é pior ainda. A resposta honesta, às vezes, é: “não foi possível consolidar este campo”. Esconder incerteza é exatamente o que o projeto prometeu não fazer.

Hoje, nada sai como verified, e isso é proposital

Em config/methodologies.yaml, todos os indicadores estão como insufficient_metadata, porque ninguém ainda confirmou que Fundamentus e StatusInvest calculam o P/L do mesmo jeito. E config/tolerances.yaml está em calibration_mode: true, porque as tolerâncias ainda não foram medidas com dados reais. Enquanto isso, o motor calcula a diferença mas grava incomparable com o motivo uncalibrated. A decisão D2 diz que dois scrapers concordando não provam que estão certos. Um sistema honesto começa conservador.

Existe ainda uma dimensão independente: o frescor. Um campo pode estar verified e ao mesmo tempo velho. Com mais de 1 dia útil ele vira stale; com mais de 5, expired (decisão D20).

5.5 Publicação: staging e a troca atômica

Gravar no banco é feito em duas fases:

  1. O coletor insere tudo em tabelas de rascunho (staging_observations, staging_validations) e confirma (commit).
  2. Numa transação separada, chama a função SQL publish_snapshot. Ela confere o lote inteiro (manifesto, valores finitos, datas coerentes) e, se tudo estiver certo, copia para as tabelas definitivas e move o ponteiro active_snapshot para o snapshot novo.

Se qualquer coisa falhar na segunda fase, o ponteiro não se move e o usuário continua vendo o snapshot de ontem, inteiro e consistente. Snapshots publicados são imutáveis: nunca são editados, só substituídos por um novo. Isso facilita muito o raciocínio sobre o sistema, porque uma resposta gravada ontem continua apontando para dados que não mudaram por baixo dela.

Analogia

É como montar a vitrine nova de uma loja nos fundos e, quando está pronta, trocar a vitrine inteira de uma vez. O cliente nunca vê a vitrine pela metade.

E se uma ação falhar no lote? Ela entra no snapshot como missing, com o motivo. O sistema não reaproveita o valor de ontem (D12), porque isso misturaria datas num snapshot que se apresenta como “o retrato de hoje”. A interface mostra a cobertura, por exemplo “11 de 12”.

6A viagem de uma pergunta

Agora o outro ritmo: o usuário digita uma pergunta. Quem atende é a Edge Function agent (supabase/functions/agent/handler.ts). Ela segue uma ordem fixa, e a ordem importa:

  1. Método HTTP. Só POST. Qualquer outra coisa é recusada.
  2. Autenticação. O JWT do cabeçalho é conferido com o Supabase Auth. Inválido? 401. É daqui, e só daqui, que sai o user_id.
  3. Autorização. O usuário está na tabela allowed_users? Não? 403. Ter uma conta Google não basta.
  4. Validação do corpo. O Zod confere o formato. Errado? 400.
  5. Idempotência. Reserva o request_id em request_runs. Se já existe com o mesmo conteúdo e terminou, devolve a mesma resposta; se está em andamento, 202; se o conteúdo é diferente, 409.
  6. Conversa. A conversa existe e pertence a este usuário? Não? 404.
  7. Ativos. Os tickers pedidos estão no universo coletado? Não? 422.
  8. Snapshot. Há um snapshot publicado? Não? 503.
  9. Evidências. Monta o pacote com os valores, estados e fontes de cada campo.
  10. Gravação. Grava a pergunta e a resposta num único INSERT e conclui a reserva.
Por que essa ordem?

As verificações baratas e de segurança vêm primeiro. Não faz sentido validar o corpo de quem nem se identificou, nem gastar uma consulta ao banco antes de saber se a pessoa pode estar ali. Isso também fecha uma porta: o cliente administrativo do banco, que ignora o RLS, só é usado depois que autenticação e autorização passaram.

6.1 Por que o user_id nunca vem do corpo

Se o servidor aceitasse {"user_id": "...", "texto": "..."}, qualquer pessoa poderia escrever o ID de outra e agir em nome dela. O JWT é assinado pelo serviço de autenticação e não pode ser forjado. Então a identidade sempre sai dele. É uma das regras que só a revisão de código pega, por isso está escrita no CLAUDE.md.

6.2 Injeção de dependência: testar sem banco

Repare na assinatura do handler:

export async function handleAgentRequest(req: Request, deps: AgentDeps): Promise<Response>

Tudo de que ele precisa (clientes de banco, relógio, função de hash, logger) chega pelo parâmetro deps. Em produção, index.ts passa os clientes reais. Nos testes, fakes.ts passa versões em memória. Isso se chama injeção de dependência, e é o que permite testar os dez passos acima na CI, em milissegundos, sem subir banco nenhum. Até o relógio é injetado, para que testes de “dado vencido” não dependam da data em que rodam.

6.3 Respostas como dados estruturados

A resposta não é gravada como texto pronto, mas como uma estrutura versionada: seções que apontam para IDs de evidência, mais uma cópia das evidências dentro da própria mensagem (D21). Duas vantagens: a conversa continua legível mesmo depois que os snapshots antigos são apagados (a retenção é de 30 dias, D11), e o relatório em PDF, no futuro, reaproveita a mesma estrutura.

6.4 E o LLM?

Na fatia atual, a função roda em modo deterministic: não há LLM. Quando entrar (tarefa T19), o papel dele será pequeno e vigiado (D4): só classificar a intenção da pergunta, devolvendo um JSON fechado validado por schema. Ele não escreve texto, não fornece números e não inventa URLs. Se o JSON vier inválido ou a cota acabar, a tela oferece um seletor manual de tickers e indicadores (D5), e a consulta nunca trava. Nos testes, o LLM é simulado (MOCK_LLM=true).

7Segurança em camadas

7.1 RLS e grants: duas travas no banco

O PostgreSQL tem dois mecanismos que costumam ser confundidos:

  • Grants dizem quais tabelas e colunas um papel pode tocar.
  • RLS (Row Level Security) diz quais linhas ele enxerga dentro da tabela.

A migration 20261114000003_rls_grants.sql começa tirando tudo (revoke all ... from anon, authenticated), porque o Supabase concede acesso amplo a tabelas novas por padrão, e depois concede o mínimo, coluna por coluna. Para os dados privados, uma política como esta garante que cada pessoa veja só o que é seu:

create policy conversations_read_own
on public.conversations for select to authenticated
using (user_id = (select auth.uid()) and (select public.is_allowed_user()));

Para os dados de mercado, o navegador simplesmente não tem grant nem política. A leitura passa obrigatoriamente pela Edge Function.

Conceito: princípio do menor privilégio

Cada parte recebe só as permissões de que precisa, e nada além. O coletor não usa a chave administrativa service_role, que ignora o RLS e daria acesso a todas as conversas. Ele usa um papel próprio, collector_ingest, que só insere no staging e executa a função de publicação (D13). Se a credencial do coletor vazar, o estrago fica limitado.

7.2 Mapa de quem pode o quê

AtorPodeNão pode

7.3 Segredos

O repositório é público (D14). Por isso:

  • Só existem arquivos .env*.example, com valores vazios.
  • Nada com prefixo VITE_ pode ser segredo: o Vite embute essas variáveis no JavaScript que vai para o navegador, onde qualquer um pode ler.
  • A CI procura padrões de chave no código (scripts/ci/check_guardrails.sh) e inspeciona o bundle final do frontend (check_bundle.sh).
  • As fixtures são sintéticas, para que nenhum dado real de terceiros vaze.

7.4 A carteira

A carteira guarda só os símbolos das ações, sem quantidade nem preço. Fica numa tabela privada com RLS de dono e nunca é enviada ao LLM (E16). É um exemplo de privacidade por design: o dado mais sensível simplesmente não tem caminho até o provedor externo.

Note quantos exemplos inválidos existem em schemas/examples/. Testar só o caminho feliz prova pouco. Os casos que devem ser recusados (um valor "NaN", uma data sem fuso, uma URL com credencial embutida) são onde os bugs de verdade se escondem.

9.2 A CI como porteiro

O workflow ci.yml roda jobs separados para regras do projeto, Python, frontend, Deno e banco, e no fim um job CI ok que só passa se todos passaram. Nenhum PR entra em fatia-acoes sem esse check e sem a aprovação do revisor.

9.3 Guardrails: regras que viram código

Algumas regras do CLAUDE.md são verificadas automaticamente por scripts/ci/check_guardrails.sh: nenhum .env real versionado, nenhum padrão de chave privada, nenhum VITE_ com cara de segredo, actions fixadas por SHA, nenhum float em valor financeiro. Uma regra que só existe num documento depende de alguém lembrar dela; uma regra que vira script é conferida em todo commit.

Outras regras não dá para automatizar (“divergência não é resolvida por média”, “o user_id vem do JWT”). Essas ficam na lista “regras que só a revisão pega”, e o sub-agente revisor (.claude/agents/revisor-tarefa.md) as confere uma a uma.

9.4 Desenvolvimento orientado a tarefas

O plano (docs/plano-execucao-fatia-acoes.md) divide o trabalho em tarefas (T01 a T25) com dependências explícitas e critérios de “pronto quando”. Cada tarefa deixa uma explicação em docs/tarefas/Txx.md. Quando algo trava, é registrado em docs/bloqueios.md e o trabalho segue para a próxima tarefa liberada. É gestão de projeto tratada com o mesmo rigor do código.

10O que ficou de fora, de propósito

Saber dizer “não” é uma habilidade de arquiteto. O README lista o que não está previsto: LangChain, LangGraph, CrewAI, Redis, banco vetorial, worker permanente, Kubernetes e servidor Python para a API.

Sem framework de agentes

O fluxo é uma sequência fixa de funções. Um framework acrescentaria uma camada de abstração para um problema que não temos, e tornaria mais difícil garantir que nenhum número venha do modelo.

Sem Redis

O snapshot no Postgres já é o cache. Um segundo armazenamento seria mais uma coisa para manter sincronizada.

Sem Kubernetes

Não há serviço permanente para orquestrar. Funções sob demanda e um job diário resolvem.

Sem Realtime nem atualização otimista

Uma consulta normal reconstrói o estado. Menos código antes de validar a ideia central.

A lição

Cada tecnologia nova traz custo: aprender, configurar, atualizar, monitorar, depurar. Só vale adicioná-la quando o problema que ela resolve já existe de verdade. Isso é o princípio YAGNI (You Aren't Gonna Need It, “você não vai precisar disso”).

11Onde o projeto está

Conforme docs/status-tarefas.md:

  • Concluído: revisão de termos das fontes, licença, estrutura do repositório, schemas, metodologia provisória, migrations, RPC de publicação, base do coletor, adaptador brapi, motor de validação, pipeline e CLI, Edge Functions agent e catalog, e a fundação do frontend com o guia de design.
  • Bloqueado: adaptadores Fundamentus e StatusInvest (T12 e T13). Os sites respondem 403 ao agente em nuvem, e o autor precisa fornecer a estrutura das páginas antes que alguém escreva um parser.
  • Pendente: classificador de intenção com LLM (T19), telas de login, chat, carteira e estado dos dados (T21b a T21f), e o relatório final.
  • Fora da leva autônoma: tudo o que exige o ambiente hospedado, segredos ou dados reais: workflow diário, calibragem das tolerâncias, avaliação de modelos e deploy.

Repare que o bloqueio de T12 e T13 não parou o projeto. Como os adaptadores implementam uma interface comum e o pipeline recebe as fontes registradas, todo o resto foi construído e testado com a brapi e com fixtures sintéticas. Esse é o retorno concreto de uma boa separação de responsabilidades.

12Exercícios para fixar

  1. Um colega sugere: “quando as duas fontes divergirem, mostra a média, que fica mais limpo”. Explique por que isso viola o objetivo do projeto.
    Ver resposta

    A média é um número que nenhuma fonte publicou, apresentado como certo. Isso esconde a incerteza, que é exatamente o que o projeto promete não fazer. O estado correto é divergent, com os dois valores lado a lado.

  2. O adaptador de uma fonte recebeu um erro de rede. Por que ele deve lançar exceção em vez de devolver uma lista vazia?
    Ver resposta

    Lista vazia parece “não há dados”, e não “houve uma falha”. A exceção permite que o pipeline registre a falha com motivo e marque o campo como missing, em vez de mostrar uma tabela vazia como se fosse legítima.

  3. Por que o coletor não usa a chave service_role, se ela “funciona para tudo”?
    Ver resposta

    Justamente porque funciona para tudo: ela ignora o RLS e daria acesso às conversas. Pelo menor privilégio, o coletor usa o papel collector_ingest, que só pode inserir no staging e publicar.

  4. O usuário clicou duas vezes em “enviar”. Descreva o que acontece no servidor.
    Ver resposta

    Os dois pedidos têm o mesmo request_id. O primeiro reserva a execução em request_runs. O segundo encontra a reserva: se ela ainda está em andamento, recebe 202; se já terminou, recebe a mesma resposta gravada. Só uma mensagem entra no histórico.

  5. Por que o número 8,50 viaja no JSON como a string "8.50" e não como o número 8.5?
    Ver resposta

    Porque o JSON.parse do JavaScript converteria o número em float, com risco de perder precisão. Como string, ele chega intacto, e as contas ficam em Decimal no Python ou em numeric no banco.

  6. Se a publicação falhar no meio, o que o usuário vê no dia seguinte?
    Ver resposta

    O snapshot anterior, inteiro. O ponteiro active_snapshot só muda dentro da transação de publish_snapshot, que é tudo ou nada. O frescor do dado vai indicar stale se ele envelhecer.

13Glossário

ADR
Registro curto de uma decisão de arquitetura, com motivo e consequência.
Adapter (adaptador)
Peça que traduz o formato de uma fonte externa para o formato interno do sistema.
Atomicidade
Propriedade de uma operação que acontece por inteiro ou não acontece.
CI (Integração Contínua)
Execução automática de testes e verificações a cada mudança enviada ao repositório.
Edge Function
Função serverless do Supabase, escrita em TypeScript e executada no Deno, que só existe enquanto atende um pedido.
Fixture
Dado de exemplo, fixo e escrito à mão, usado em testes para não depender de serviços reais.
Grant
Permissão SQL para um papel acessar uma tabela, coluna ou função.
Idempotência
Repetir uma operação produz o mesmo efeito que fazê-la uma vez.
Injeção de dependência
Passar a uma função as coisas de que ela precisa (banco, relógio), em vez de ela mesma criá-las. Facilita testes.
JWT
JSON Web Token: credencial assinada que prova quem é o usuário.
Migration
Arquivo SQL versionado que altera o esquema do banco de forma reprodutível.
Observação
Um indicador, de um ativo, em uma fonte, com toda a sua proveniência.
Proveniência
A história de um dado: de onde veio, quando, como foi calculado.
RLS
Row Level Security: políticas do Postgres que filtram quais linhas cada usuário enxerga.
RPC
Chamada de uma função no servidor, aqui uma função SQL como publish_snapshot.
Snapshot
Retrato imutável de todos os dados coletados num lote. O ativo é indicado por active_snapshot.
Staging
Área de rascunho onde o lote é gravado antes de ser conferido e publicado.
Tolerância (atol, rtol)
Diferença máxima, absoluta ou relativa, para considerar que duas fontes concordam.
YAGNI
“You Aren't Gonna Need It”: não construa o que ainda não é necessário.
